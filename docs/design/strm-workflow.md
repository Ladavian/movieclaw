# 网盘 strm 工作流：整理输出目录与库根解耦——设计

> 状态：设计定稿（2026-08-02），待实施。
> 源起：issue #44（二级分类跟目录问题）、issue #39（strm 识别，已验证可用）。
> 关联文档：[library.md](library.md)（媒体库架构）、
> [library-routing.md](library-routing.md)（路由与"订阅止于投递"语境）。

## 0. 问题定位

### 0.1 网盘 strm 玩法的目录三角

PT + 网盘用户的典型工作流涉及**三个**目录，而 movieclaw 现有模型假设
后两者是同一个：

```
下载目录（保种，PT 原名，不可动）
   │  硬链 + 识别 + 重命名（movieclaw 的核心价值）
   ▼
中转目录（规范命名的真实文件 —— 上传网盘后即可删除）
   │  上传网盘 + 生成 strm（外部工具，movieclaw 不参与）
   ▼
媒体库根（只放 strm 占位文件 —— Emby/Jellyfin 扫这里）
```

现状的绑定点在 `derive_save_path(library)`：整理输出的落点恒等于库主根。
于是真实大文件被硬链进本该只放 strm 的库目录（issue #44 的核心抱怨
"硬链接文件夹无法自定义，媒体库文件夹又是 strm 文件夹"）。

### 0.2 issue #44 的两条诉求拆解

| 诉求 | 结论 |
|---|---|
| "没有二级分类" | 区域/类型粒度已由**多库 + 收藏范围**覆盖（library-routing.md），回复引导即可；单库内分目录形态是既有 v2 开口（库内二级目录），本设计不涉及 |
| "硬链接目录无法自定义" | **真实缺口**，本设计解决 |

### 0.3 讨论中否决的备选（2026-08-02，与用户逐一推演）

1. **把中转目录建成一个库**：上传后删除本地文件会触发缺失告警，
   strm 侧反而游离在管理之外——库的台账语义与"过客文件"根本冲突；
2. **中转目录作为监听导入源、目标仍是库**：重命名发生在入库环节，
   中转里还是乱名文件，上传上去 strm 结构就是乱的；且真实文件最终
   仍落进 strm 库，问题只是往前挪了一格；
3. **监听导入规则增加"自定义路径"目标（规则级）**：能解监听导入
   一条路，但订阅认领、自动路由、多库分流都锚在"库"上——路径目标
   绕开了库，这些能力全部丢失，订阅兼容要另起炉灶；
4. **"原样转移不经过刮削"模式**：与需求相反（网盘端结构由上传前的
   命名决定，必须先改名）；且无识别的搬运用 qB 分类 + 脚本即可完成，
   movieclaw 不提供增量价值。

## 1. 方案：库级「整理输出目录」

库表新增一个可选路径 `staging_root`（整理输出目录，网盘中转根）。
**配置了它的库，一切整理输出动作换根落到中转；库根退化为纯"回流侧"**，
由既有扫描/实时监控接纳外部工具镜像回来的 strm。

为什么是库级而不是规则级——三个既有架构事实让它几乎免费：

1. **落点推导单点收口**：`derive_save_path(library)` 是所有整理落点的
   唯一推导口（监听导入 `_ingest_entry`、手动下载 save_path 预选）。
   库上换根，全部消费点自动继承；
2. **订阅止于投递**（download_progress.py）：订阅不亲自搬运，下载完成
   由监听导入按 info_hash 认领 → 目标库 = 订阅定格库 → 落点跟库走。
   路由、粘性、多库分流（华语库/动漫库各配各的中转）**零改动保留**；
3. **工单由库存对账关闭**（wanted_fulfillment.py）："库里有"才算完成。
   整理到中转时库里还没有 → 工单保持在途；strm 回流经扫描入账 →
   对账关闭工单、时间线补记"已入库"。**"上传中"这个在途状态被现有
   机制天然正确地表达**，不需要任何新状态机。

完整链路（仅第一段是新行为，其余全是现状）：

```
下载目录 ──[监听导入：识别+重命名，换根]──▶ 中转目录        ← 本设计唯一改动
中转目录 ──[外部：上传网盘 + 生成 strm]──▶ 库根             ← movieclaw 不参与
库根 ──[现有：扫描/实时监控收 strm → 识别入账]──▶ 台账      ← 零改动（#39 已验证）
台账 ──[现有：库存对账]──▶ 工单关闭、订阅进度、时间线        ← 零改动
```

**命名规范同源是两段之间唯一的衔接机制**：中转目录按库同款规范命名
（`{title} ({year})/…`），strm 生成工具照网盘结构镜像，回流文件名
天然规范 → 扫描识别精准命中。不发明任何显式的关联协议。

## 2. 行为定义

### 2.1 落点换根

`staging_root` 非空时，`derive_save_path` 及监听导入的条目落点推导
以中转根替换主根，命名规则不变。覆盖全部整理入口：

- 监听导入（指定库规则、auto 路由规则、info_hash 认领订阅身份）；
- 手动下载弹窗的 save_path 预选（下载器直接落到中转的条目目录）。

### 2.2 输出侧是"过客"，不入台账

整理到中转的文件**不写 library_file 台账、不生成海报/nfo 资产**——
它们上传后就会被删除，入账只会制造缺失告警。识别产生的 `media_item`
身份档案照常建立（回流入账与订阅对账都依赖它）。ffprobe 完整性门禁
保留（挡残缺文件的价值与落点无关）。

入库结论文案相应改写，例如：
"已识别为《风筝》，硬链接到中转目录（等待上传网盘后以 strm 回流入库）"。

### 2.3 回流侧：零改动

库根扫描/实时监控本就接纳 `.strm`（layout.py 的 `SCAN_VIDEO_EXTS`），
识别按文件名走，规格列留空（strm 无媒体流，ffprobe 无意义）。
strm 入账后 `close_fulfilled_wanted` 照常关闭工单。#39 已确认此路可用。

### 2.4 订阅兼容性（本设计的验收重点）

| 环节 | 行为 | 改动 |
|---|---|---|
| 路由与定格 | 收藏范围选库、创建时定格 `library_id` | 无 |
| 投递 | `resolve_dispatch_dir`（专属规则 → 同 kind auto 规则） | 无 |
| 完成搬运 | 认领 → 定格库 → **落点 = 该库中转根** | 仅换根 |
| 工单关闭 | strm 回流入账 → 库存对账关闭 | 无 |
| 救援巡检 | 卡死/删种判定基于下载器状态，与回流无关，不会误退回重下 | 无 |

在途语义：种子下载完成、已整理到中转、strm 未回流期间，工单停在
GRABBED——这是**正确的**："库里有"才是订阅的完成定义。风险见第 6 节。

### 2.5 校验（保存时前置报错，中文文案）

- 中转根不得与任何库根、任何监听导入源目录重叠；多库各配中转时
  互不重叠（同根会导致条目目录碰撞）；
- 硬链接同盘检测的锚点从库主根改为中转根（配置了它的库）：
  "监听目录与「电影库」的整理输出目录不在同一文件系统，硬链接会失败；
  请改用「复制」策略，或调整存储布局"；
- 链路体检（订阅设定页）的转移段同步换锚，并对配置了中转的库加一条
  说明性结论："入库依赖网盘回流（外部工具），movieclaw 只负责整理到
  中转目录"。

## 3. 数据模型

| 表 | 改动 | 说明 |
|---|---|---|
| `library` | + `staging_root` str nullable | 整理输出目录（网盘中转根）；NULL = 现状（输出即库根） |

加列迁移，SQLite 走 alembic batch，可平滑升降。无其他 schema 改动。

## 4. 交互设计

- **库表单**新增"整理输出目录"配置（默认收起，归入高级/网盘玩法区），
  说明文案讲清三角结构："配置后，下载整理的真实文件落到此目录（供
  上传网盘，上传后可删除）；库根目录只需放置网盘生成的 strm 文件，
  movieclaw 会自动扫描入库。不配置则维持现状。"
- **库卡片**：配置了中转的库加一个"网盘中转"徽标；
- **监听导入表单**：无改动（目标仍是库/自动路由，落点由库决定）；
- **订阅时间线**：认领整理的活动文案带中转语境（见 2.2）。

## 6. 边界与风险

1. **回流断链无原生提醒**：上传工具挂掉时工单长期在途，movieclaw
   不误退回（救援只看下载器状态），但也不知道链路断了。v1 接受
   （体检已有说明性结论提示外部依赖）；若反馈强烈，v1.1 加"整理入
   中转超 N 天未见回流"的时间线提醒，判定素材（整理时间、条目身份）
   都已在账；
2. **strm 库的规格与洗版降级**：strm 无媒体流，规格列为空，按规格
   洗版在网盘库不可用；且替换发生在网盘侧，movieclaw 无法执行。
   文档与界面不对网盘库承诺洗版；
3. **strm 生成端须按库分根**：多库用户（华语库/动漫库）各配中转、
   网盘端相应分目录，strm 镜像才会落进正确的库根。这是外部工具的
   配置约定，写进用户文档；
4. **内置上传 + strm 生成**：明确不做，留作独立开口——那是把外部
   环节纳入管线的产品级决策（网盘认证、限速、失败重传……），与
   本设计正交，届时第一段与回流侧无需变更。

## 7. 决策记录（2026-08-02）

1. 解耦落在**库级** `staging_root`，不做规则级路径目标（订阅认领、
   路由、多库分流都锚在库上，库级换根让它们零改动继承）；
2. 中转是"过客"：不入台账、不生成资产、ffprobe 门禁保留；
3. 两段衔接 = 命名规范同源，不发明显式关联协议；
4. 在途语义复用"库存对账关闭工单"，不加新状态机；
5. 否决"原样转移"模式（与需求矛盾、无增量价值，见 0.3）；
6. issue #44 的二级分类半边：引导多库 + 收藏范围，单库分目录维持
   既有 v2 开口不变。
